# 数据库补丁执行说明

本目录保存从旧版 `ganlu.sql` 升级到当前各功能模块所需的增量脚本。正式库执行前必须先做完整备份；不要把生产数据库密码写进脚本或提交到 Git。

## 规定顺序

| 顺序 | 文件 | 作用 | 当前状态 |
| --- | --- | --- | --- |
| 1 | `00_user_security.sql` | 用户名/手机号唯一约束、密码列长度 | 已提供 |
| 2 | `10_team_core.sql` | 团队风采核心表迁移 | 已提供 |
| 3 | `11_team_content.sql` | 团队风采内容管理 | 已在依赖 PR #12 提供，尚未进入当前集成分支 |
| 4 | `12_public_image_quota.sql` | 公共图片永久数量/容量原子账本 | 已提供 |
| 5 | `20_message_board.sql` | 留言与回复查询索引 | 已提供 |
| 6 | `30_material_center.sql` | 课件中心字段、索引和上传会话表 | 已提供 |
| 7 | `40_volunteer_application.sql` | 志愿者报名表及处理中手机号唯一约束 | 已提供 |

全量联调必须等孙木文按 `PR #5 → PR #12` 完成审核与集成后，在数据库备份副本中按上表顺序重新验证。不要从依赖分支单独复制脚本或自行编造同名空脚本。

## 全新本地数据库

1. 用 MySQL Workbench 创建字符集为 `utf8mb4` 的 `ganlu` Schema。
2. 先执行根目录 `ganlu.sql`。
3. 为了运行当前已交付模块，可依次执行 `00`、`10`、`12`、`20`、`30`、`40`；其中部分变更已经进入基线，脚本会跳过已存在的索引或表。PR #12 合入并提供 `11` 后，完整顺序为 `00 → 10 → 11 → 12 → 20 → 30 → 40`。
4. `10_team_core.sql` 会创建迁移备份表，并会拒绝重复或部分执行。若它报错，停止操作并保留提示，不要直接删备份表重跑。
5. PR #12 合入后，建议重新创建一份干净的本地库，从基线开始按完整规定顺序验证。

## 已有数据库

1. 先导出“结构 + 数据”的完整备份，并在另一 Schema 中实际恢复一次。
2. 检查空用户名、重复用户名、重复手机号、非法团队年份及重复的处理中报名；`00`、`10`、`40` 检测到问题会主动停止。
3. 在备份副本执行补丁并核对表、索引和历史数据数量。
4. 记录每个脚本的执行时间、执行人、结果和错误信息。
5. 只有孙木文确认备份可恢复、PR #12 已按顺序集成、所有模块验收通过后，才能在正式库执行。

## 当前限制

2026-08-02 的集成环境中 MySQL84 Windows 服务在运行，但 `mysql` 命令未加入 `PATH`，且集成人员没有数据库凭据。因此本轮只完成了 SQL 静态审查，没有对任何本地或生产数据库执行脚本。详见 `docs/integration/最终联调记录.md`。

## 权限和校验要求

1. `GET /message/list` 对游客开放，只返回 `status=1` 的留言/回复。
2. `POST /message/add` 和 `/message/addReply` 要求登录；level=0、1、2 均允许。
3. 删除接口允许 level=0 和 level=1，level=2 必须返回 403。删除权限不按内容是否本人发布区分。删除留言时留言逻辑删除，其回复也应在查询中不可见；不物理清除审计数据。
4. 后端从赵友为提供的 `AuthContext` 取当前用户 ID，忽略/拒绝请求中额外的 `userId/userid`。
5. 留言 `trim` 后 1～500 字，回复 1～300 字；无效 messageId、已删除留言、非法分页参数返回明确 400/404。
6. `page>=1`，`pageSize` 限制 1～50，避免任意大页拖垮数据库。
7. 正文作为纯文本保存和返回，不存 HTML；日志不要打印完整留言正文和用户敏感信息。

## 数据库补丁要求

在 `20_message_board.sql` 中检查并补充：

- `message(status, create_time)` 组合索引。
- `reply(message_id, status, create_time)` 组合索引。
- 必要的用户/留言外键或数据完整性检查；添加外键前先处理孤儿数据。
- 不 DROP 原表，不清除已有留言。

如果保留软删除，删除用户时的历史展示策略要在说明中写清，不要使用会级联物理删除历史留言的配置。

## 查询优化要求

列表查询一次取得当前页留言，再用一条 `WHERE message_id IN (...)` 查询所有回复并在 Java 中分组；用户展示名尽量通过 JOIN 一次带回。禁止每条留言和每条回复各查询一次用户。

分页排序使用 `create_time DESC, id DESC` 保证同一时间下稳定。返回 `messages`、`total`、`page`、`pageSize`。

## 必测场景

- 游客列表成功，游客新增/回复返回 401。
- 管理员、团队和学生都能新增留言、回复。
- 管理员和团队删除留言/回复成功，公开列表不再显示。
- 学生账号在请求体伪造管理员或团队用户 ID 删除，仍返回 403。
- 空白、超长、已删除 messageId、page=0、pageSize=1000。
- 11 条数据、pageSize=10 时总数和第二页正确。
- 批量回复查询不会出现明显 N+1 SQL 日志。

## 验收标准

- 请求体中不需要也不信任 userId。
- 角色矩阵与总览一致，所有失败状态有合适 HTTP 状态码。
- 已有留言迁移后仍可读取，SQL 补丁不会 DROP 表。
- 测试覆盖伪造身份和分页边界，`.\mvnw.cmd test` 通过。
